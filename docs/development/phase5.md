# Phase 5 — simulated deployment engine

The agent can execute **signed development simulations**. This phase introduces a durable
job state machine, authenticated admission, lease renewal, restart recovery, reporting,
cancellation and simulated failure/rollback. It never downloads a URL, runs an installer,
extracts an archive, changes installed software, launches a process or reboots the machine.
Real deployment adapters and their native acceptance remain future work.

## Enable a development simulation

Use the normal mock/agent setup in the root README. Generate a dedicated development key pair:

```sh
go run ./tools/mock-server/cmd/simulation-keygen
```

The command prints JSON with `publicKey` and `privateKey`. Keep this private key out of source
control and logs. Provision the returned values into the respective process environments:

```sh
# Mock server terminal, before starting the mock:
export KIOSENTRA_MOCK_SIMULATION_PRIVATE_KEY='<privateKey from the generator>'

# Agent terminal, before starting the agent:
export KIOSENTRA_DEVELOPMENT=true
export KIOSENTRA_SIMULATED_DEPLOYMENTS=true
export KIOSENTRA_SIMULATION_PUBLIC_KEY='<publicKey from the generator>'
export KIOSENTRA_INTERVAL=5s
```

The flag defaults to false. Enabling it without development mode or a valid 32-byte base64
Ed25519 public key fails configuration validation. A mock without a signing key continues to
produce untrusted jobs, which are rejected. Previously rejected job IDs stay rejected; create
a new job after enabling simulation. Keep the mock running while restarting the agent because
mock registrations and idempotency receipts remain in memory.

After enrollment, get the device ID from authenticated `/dev/state` as documented in the README.
Create a job from a terminal with the mock admin token configured:

```sh
# Substitute the enrolled UUID for <device-id>.
curl --fail --silent --show-error \
  -H "Authorization: Bearer $KIOSENTRA_MOCK_ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"deviceId":"<device-id>","kind":"deployment","targetVersion":"2.0.0","leaseSeconds":300,"scenario":"success"}' \
  http://127.0.0.1:8080/dev/jobs
```

`scenario` is optional on this development endpoint and defaults to `success`. Supported fixtures:

| Scenario | Result |
| --- | --- |
| `success` | succeeded |
| `download_failure` | failed during simulated download |
| `hash_failure` | failed before installation on SHA-256 mismatch |
| `install_failure` | rolling_back → rolled_back |
| `validation_failure` | rolling_back → rolled_back |
| `rollback_failure` | rolling_back → failed |
| `timeout` | simulated installer timeout → failed |

These are deterministic fixture outcomes. `timeout` does not sleep or test termination of a
real child process, and `download_failure` does not exercise real HTTP transfer interruption.

## Admission and trust

Only `kind=deployment`, `packageType=simulation`, matching target/release versions and the
`development-simulation-v1` key ID are eligible. Release URLs must exactly identify one of the
fixture names at `https://simulation.invalid/`; **they are identifiers, never fetched**.
Signatures bind the enrolled device ID, job ID, kind, target and complete release metadata
(excluding its signature) using the canonical JSON generated by
`contracts.SimulationSigningBytes`. Lease expiry is excluded because renewal changes it.
The signature is checked before acceptance and again before resuming a persisted checkpoint.
The fixture size and SHA-256 are checked before advancing to `installing`.

This development signing convention is not a real release-signature format. MSI, EXE, ZIP,
kiosk, configuration packages remain unsupported by the deployment engine. Phase 6 handles signed agent-update
simulations through a separate opt-in helper. A URL or structurally valid
signature alone is never sufficient. At most one simulation is active; additional jobs are
rejected as busy, rather than silently queued. The central service must submit a new job ID
if it wants to retry a rejected request.

## State and recovery

A normal run follows:

```text
accepted → downloading → verifying → installing → validating → succeeded
                                              ↘ rolling_back → rolled_back
```

Failures may end in `failed`; lease loss, local disablement or authorized cancellation ends in
`cancelled`. Terminal states cannot restart. Every transition and its status report ID are
committed together in SQLite. Admission and the initial accepted state are also one transaction.
The immutable job decision is acknowledged before progression or status reporting.

Each service cycle performs at most one instantaneous simulation step. Before each step it
flushes pending reports and requests a 300-second lease. Renewal retries use the same persisted
idempotency key for that checkpoint. Unknown renewal outcomes pause progression; an expired,
missing or invalid lease cancels the simulation. A ten-minute persisted overall deadline bounds
the run. Reconciliation runs at the beginning of each cycle, even during central-sync backoff.
Choose a collection interval shorter than the lease; longer intervals can intentionally expire it.

There is no installer or background renewal worker in this phase. The pure simulator has no
external effects and every checkpoint is a safe pause point. Restart resumes the next step only
after trust, deadline, acknowledgement and lease checks. Shutdown pauses the run; it does not
claim to have installed or rolled back anything. Disabling simulation or changing its trust key
causes active work to terminate on reconciliation.

Phase 5 introduced schema 2, which adds `deployments` and `deployment_events`, preserving schema-1 records in a
transactional additive migration. Older agents reject schema 2. Back up state with a WAL-aware
procedure before upgrading; there is no automatic downgrade. Phase 6 advances the service schema to 3 for update handoffs. The existing 10,000-job ledger
cap bounds retained jobs, and the finite acyclic state machine bounds events per job. Records
are not pruned because they also provide replay protection.

Status events use a dedicated ordered durable queue, independent of bounded telemetry. Successful
reports are retained as history. A server 404/410 marks a report `unavailable` while preserving
local history, so expired jobs cannot permanently block telemetry delivery. Transport errors
retain the report and prevent further simulation progress. Other protocol errors are surfaced
for operator investigation. Collection continues while sync is backing off.

## Local console

Deployments shows the newest 100 simulation transitions with progress, timestamp and report
status, plus job decisions. All results are labelled as simulations. Full release payloads,
signatures and trust keys are excluded from the IPC projection.

Maintenance includes **Cancel active simulation**. The existing technician-secret flow issues a
single-use, expiring `cancel_deployment` grant; view access cannot cancel a job. The service queues
the action and records a terminal state at its next safe loop boundary. An acknowledgement means
the request was received, not that a particular job has already been cancelled. Cancelling with
no active simulation has no effect. Exiting the console leaves the service running.

## Validation

Automated coverage includes scenario outcomes, signature/device binding, strict optional request
fields, single-job admission, duplicate IDs, schema migration, atomic history, restart at every
simulated checkpoint, lost ACK/status/renewal replies, lease expiry, disabled/changed trust,
overall deadline, cancellation, report replay and continued telemetry during deployment.
UI tests cover history labels and scoped cancellation. See [validation record](validation.md).

Windows runtime acceptance remains outstanding, including the earlier SCM/DPAPI/Session 0 and
console checklists. This phase does not validate real download resume, archive extraction,
installer timeout/termination, native rollback or a reboot during external installation effects.
Those tests must accompany future real adapters before enabling installation.
